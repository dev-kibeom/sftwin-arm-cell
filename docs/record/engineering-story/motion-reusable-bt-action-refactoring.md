# Motion 실행 구조를 재사용 가능한 BT Action으로 분리한 과정

*Engineering Story — 2026-10-30 설계자 회고와 PR 이력을 바탕으로 작성한 역사적 기록. 현재 CDS/FDS/ICD의 규범적 계약이나 Acceptance Report를 대체하지 않는다.*

## 문제와 설계 의도

초기 Motion의 파지 Pose 탐색과 IK 최적화는 성공률과 계획 시간을 개선하기 위한 알고리즘 문제였다. 이 과정은 PICK IK 탐색 발전 기록에 이미 정리되어 있다. 이후의 문제는 알고리즘이 복잡해진 실행 구조에 묶여 있으면 계획 단계, 검증 단계, 실행 단계 또는 전체 작업 시퀀스를 교체하거나 추가하기 어렵다는 점이었다.

설계자가 BT 구조로 개편한 **일차적 이유는 탐색·계획·실행을 재사용 가능한 Action으로 분리하여 향후 변경과 확장을 쉽게 만드는 것**이었다(2026-10-30 직접 회고). 이는 BT를 도입했다는 기술 선택 자체보다, 개별 연산의 계약과 조합 구조를 분리하려는 의도다. 특히 **PICK·PLACE 실행 전략을 유연하게 조합하고 비교하는 것**이 가장 중요한 확장 방향이었다. 설계자는 시퀀스도 정책의 일환으로서 변경과 확장이 자주 발생한다고 판단했고, 따라서 개별 연산의 분리만이 아니라 시퀀스 구성 구조 자체를 리팩토링할 가치가 있다고 보았다. 계층별 책임 명확화는 이 목표를 실현하는 구조적 결과이지, 이번 회고에서 별도로 확인된 최초 동기로 간주하지 않는다.

## 단계별 전환과 근거

1. **계획과 실행을 다른 책임으로 분리 — PR #679.** 기존 결합 호출 안에서 plan-only와 저장 Trajectory 실행을 분리했다. `MotionPort::planMotion()`은 경로를 계산하되 실행하지 않고, `executePlannedMotion()`은 확인된 저장 계획을 다시 계획하지 않고 실행한다. 이를 통해 작업 SubTree는 필요에 따라 선행 계획을 확보하고 실행 순서를 구성할 수 있게 됐다. 기존 lifecycle·Safety 계약은 유지했다.
2. **PICK 탐색의 물리 연산을 C++ 책임 단위로 분리 — PR #711.** Grasp IK, FK/Bounds, Contact, State Collision, Approach IK 및 Path Planning을 독립 함수·모듈로 추출했다. 이 단계에서는 기존 탐색 루프와 순서·Retry를 보존해 동작 변경이 아닌 책임 분리에 집중했다.
3. **BT의 구체 Action으로 운영 경로 전환 — PR #714.** PICK Approach의 15개 구체 단계가 BT.CPP Action 타입으로 직접 등록되도록 하고 문자열 dispatcher를 제거했다. 공통 PlanningLeaf는 Context·중단·Budget·진단 타이밍 등 공통 기반으로 한정하고, 각 구체 Node가 해당 연산을 호출했다. 진단 집계도 실행 상태 변조와 분리했다.
4. **여러 작업에서 공통 Action을 조합 — PR #678.** PICK·PLACE·교란 SubTree가 계획과 저장 계획 실행 Action을 공통으로 사용하도록 정리했다. 교란은 전체 구간 계획을 확보한 뒤 실행하는 등 작업별 순서와 실패 전환 정책을 SubTree가 소유한다. 따라서 Action 재사용은 세 작업을 동일한 시퀀스로 강제하는 것이 아니다.

## 최종적으로 분리된 책임

- **Orchestration:** 미션·배치 진행과 재진입 및 상위 복구 흐름.
- **Task Execution BT:** PICK·PLACE·교란의 작업 단계, 후보 전환, 전략 선택과 작업 단위 복구. 공통 Plan/Execute Action을 작업별 SubTree로 조합.
- **Motion Planning BT와 연산:** PICK의 Pose·Seed 탐색, IK·충돌·경로 계획의 세부 계산 및 탐색 흐름. 하위 연산은 가능한 한 독립적인 입력·결과를 가지며 특정 상위 작업 정책을 중복 소유하지 않음.
- **Motion runtime/Port:** 개별 movement의 계획·실행·측정 완료와 Cancel/Safety lifecycle. 실행 과정의 단일 로봇 상태 및 backend authority.

현재 소유권 및 불변조건의 원문은 [Task Execution CDS](../../design/components/task-execution/cds.md)와 [Motion CDS](../../design/components/motion/cds.md)를 따른다. 이 기록은 해당 문서의 구현 세부 계약을 복제하지 않는다.

## 적용 이후의 설계자 평가

설계자 후속 회고(2026-10-30)에 따르면, 리팩토링 이후 **실제 수정·기능 확장·디버깅이 용이해졌음**을 체감했다. 이 회고는 실행 전략과 시퀀스가 정책에 따라 달라지는 프로젝트에서 재사용 가능한 Action과 SubTree 조합을 선택한 이유를 뒷받침한다. 다만 개발 시간 단축률이나 변경 파일 수 감소처럼 정량화된 효과를 측정한 비교 실험은 아니므로, 특정 수치의 생산성 향상으로 해석하지 않는다.

## 채택한 접근의 의미와 대가

- **선택:** 시퀀스·후보 정책을 작업 SubTree에, 개별 작업을 재사용 가능한 Action에, 기하학·IK·Collision·Planning 계산을 낮은 수준의 연산에 배치한다.
- **피한 결합:** 특정 PICK 루프가 모든 연산을 직접 실행하고 진단을 집계하는 구조, 또는 공통 Action에 작업별 후보 전환·Retry를 숨기는 구조.
- **대가:** Context와 Action 입출력, 중단·예산 관리, Plan identity 및 상태 소유권을 정확히 정의해야 한다. Action 수가 늘었다는 사실 자체가 성능 개선이나 재사용성 검증을 의미하지는 않는다.
- **변경 가능성:** 알고리즘의 내부 구현 교체, 작업 순서 변경, 새로운 SubTree의 공통 Action 조합을 서로 다른 변경 범위로 다룰 수 있다. 단 실제 확장 작업에서 어느 정도 코드 변경이 절감되는지는 별도 사례로 검증해야 한다.

## 검증 범위와 미측정 효과

위 PR은 각각 빌드·집중 회귀 테스트를 보고했다. 특히 #678은 Task Execution CTest 및 Motion의 관련 집중 테스트 통과를 기록했지만, 두 ROS launch integration 테스트는 격리 환경의 네트워크 제한으로 미확인 상태였다. 따라서 이 이력을 근거로 전체 라이브 시퀀스의 성능·안정성이 개선되었다고 주장하지 않는다. 이번 기록 작업은 실행 코드를 변경하거나 새 라이브 테스트를 수행하지 않았다.

## 후속 확인 질문

후속 회고에서 최우선 확장 시나리오는 **PICK·PLACE 실행 전략의 유연한 조합과 비교**였음이 확인됐다. 시퀀스 자체의 변경 빈도가 높다는 판단이 구조 개편의 직접적인 동기였으며, 적용 이후 수정·확장·디버깅이 편리해졌다는 경험적 평가도 확보했다. 정량적인 유지보수성 비교 자료는 별도 검증 과제로 남긴다.
