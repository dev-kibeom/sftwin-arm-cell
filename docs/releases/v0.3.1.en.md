# SF-Twin ARM Cell v0.3.1 Release Notes

> v0.3.1 retains the v0.3.0 ROS architecture while improving local and Docker run paths for Isaac Sim and the ROS runtime. It is an engineering and simulation release.

## Improvements since v0.3.0

- **Two ROS run modes:** The project documents running a ROS 2 Humble workspace built on the host, or having Docker Compose build the image and start the production bringup.
- **Selectable logging and diagnostics:** Host launch arguments or Docker's `ARM_CELL_LOG_LEVEL` and `ARM_CELL_DIAGNOSTICS` select `info`/`debug` logging and component diagnostic capture independently. By default, `info` disables optional capture and `debug` enables all ROS diagnostic producers.
- **Isaac Sim no longer needs a local ROS workspace build:** `isaac_arm_cell.sh` prepares the scene, Timeline, and UI Hub. When the host ROS workspace `install` is absent, Isaac connects over localhost TCP to the Material and Hub Python 3.10 sidecars running in Docker. The sidecars listen for connections, including when Isaac starts later.
- **Docker DDS data delivery:** Compose defaults Fast DDS transport to `UDPv4`. This resolves the case where Docker discovered publishers but received no samples. RGB, depth, CameraInfo, simulation clock, and joint-state topics from Isaac Sim were observed in ROS.
- **MoveIt planning-only initialization:** The Docker image now installs the `moveit_simple_controller_manager` runtime dependency, and the planning-only profile explicitly configures the manager.
- **Consolidated run instructions:** The host ROS and Docker Compose procedures are in the README; this release note records the implementation changes.

## Verification scope and known limitations

- The combined Isaac Sim and Docker Compose runtime was confirmed to start and communicate, including RGB-D topic delivery. The README also documents the host ROS 2 Humble run path.
- This release does not claim a full ROS test-suite pass, every Mission/fault/recovery scenario, or complete Final Mission Acceptance.
- The intermittent RGB-D pair acquisition issue was resolved in v0.3.0 and remains resolved in later versions. The v0.3.1 UDPv4 setting addresses the separate Docker DDS topic-delivery problem. RGB-D topic delivery alone does not establish Vision detection or PnP success. Historical observations remain in the [RGB-D acquisition record](../record/engineering-story/vision-rgbd-intermittent-acquisition-failure.md).
- Physical-robot operation and safety-rated E-stop/STO hardware are outside the verified scope.
